# ПЦ Спорт — PWA

Одностраничное приложение для челленджа: нормы на день, отработка после форс-мажора, журнал и счёт по штрафам. Без сборки — статика, любой хостинг.

## Навигация (v18)

Внизу — четыре вкладки: Сегодня, Журнал, Чат, Настройки. Счёт и Правила — компактные кнопки сверху на «Сегодня»; на кнопке «Счёт» сразу видна общая сумма долгов, не нужно заходить внутрь. Чат живёт только внизу, в одном месте — не дублируется больше нигде (было по ошибке сразу в двух местах с одинаковым `id="chat-dot"` — HTML такого не допускает, это баг предыдущей версии).

## Что считает само

- **Чередование.** У Коли и Вани подтягивания и отжимания идут через день от опорной даты (настройки → «Отсчёт чередования»). По умолчанию 17.08.2026 — день подтягиваний.
- **Отработка.** Каждый подряд идущий день со статусом «Форс» повышает множитель следующего дня: ×2 → ×3 → ×4, дальше не растёт. На карточке видно и итог, и разбор (`60 × 3`).
- **Штрафы.** Пропуск и добровольный выход дают 5000 ₽, которые делятся поровну между теми, кто участвует в челлендже **на дату штрафа**. Выбывшие в делёж не попадают. Вкладка «Счёт» показывает баланс каждого: сколько заплатил, сколько получил, сколько в итоге.
- **Альтернативы.** Считает израсходованные за неделю (пн–вс) и подсвечивает превышение лимита в 2 раза.

Статус дня ставится на вкладке «Сегодня» или тапом по клетке в журнале (перебор по кругу).

## Развёртывание на GitHub Pages

2. Settings → Pages → Source: `main`, папка `/root`.

## Синхронизация — по схеме Herald Chat

Токенов в приложении нет вообще. Клиент знает только URL одной облачной функции и делает один вид запроса:

```
POST <URL функции>
{ "action": "get_state" | "save_state" | "ping", ...params }
```

Сама функция (папка `backend/`) сама лезет в Яндекс.Диск и в Lockbox за токеном — токен не хранится статичной строкой нигде, включая переменные окружения: там лежит только `refresh_token`, а рабочий `access_token` функция обновляет сама и складывает обратно в Lockbox. В браузер не попадает ничего.

### Разовая настройка бэкенда (один раз на весь чат)

Архитектура — точная копия Herald Chat: OAuth-токен Яндекс.Диска не лежит статичной строкой в переменной окружения (он всё равно протухает раз в год), а хранится в **Yandex Lockbox** вместе с `refresh_token` и сам обновляется функцией по мере истечения. Функция читает Lockbox через IAM-токен своего сервисного аккаунта — человек в эту цепочку не входит вообще.

**1. OAuth-приложение Яндекса.**
На https://oauth.yandex.ru/ → «Создать приложение» → веб-сервис, права `cloud_api:disk.read` + `cloud_api:disk.write`, Callback URL можно `https://oauth.yandex.ru/verification_code`. Получить `Client ID` и `Client Secret`.

**2. Секрет в Yandex Lockbox.**
В консоли облака создать секрет с одним ключом `state` (тип «текст»), значение пока любое — перезапишется на шаге 4. Запомнить `LOCKBOX_SECRET_ID`.

**3. Сервисный аккаунт.**
Создать сервисный аккаунт с ролями `lockbox.payloadViewer` и `lockbox.editor`. Привязать его к будущей Cloud Function (на шаге 5).

**4. Бутстрап — получить первый refresh_token.**
Разово, вручную, с компьютера:
```
# открыть в браузере и авторизоваться под тем аккаунтом Яндекса,
# на чьём Диске будет жить состояние челленджа:
https://oauth.yandex.ru/authorize?response_type=code&client_id=<CLIENT_ID>

# Яндекс покажет код подтверждения — обменять его на токены:
curl -X POST https://oauth.yandex.ru/token \
  -d grant_type=authorization_code \
  -d code=<КОД_ИЗ_БРАУЗЕРА> \
  -d client_id=<CLIENT_ID> \
  -d client_secret=<CLIENT_SECRET>
```
Ответ (`access_token`, `refresh_token`, `expires_in`) собрать в JSON вида
`{"access_token":"…","refresh_token":"…","expires_at":<unix-время истечения>}`
и записать этой строкой в ключ `state` секрета Lockbox (шаг 2). Дальше функция обновляет его сама — вручную это нужно сделать один раз.

**5. Yandex Cloud Function.**
Среда `python3.12`, обработчик `index.handler`, привязать сервисный аккаунт из шага 3. **Деплой строго ZIP-архивом** — из-за `boto3` (нужен для видео, см. «Хранилище видео» ниже) через веб-редактор код не задеплоить, pip install оттуда не запускается. В архив (или в загружаемую директорию) кладутся `backend/index.py` и `backend/requirements.txt` рядом, на одном уровне.

**Переменные окружения функции:**
- `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` — из шага 1;
- `LOCKBOX_SECRET_ID` — из шага 2;
- `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` — для видео, см. раздел «Хранилище видео» ниже (можно добавить позже, если сначала хочется поднять только состояние/чат).

**6. Публичный доступ** — включить вызов без IAM-токена (публичная функция), скопировать URL вида `https://functions.yandexcloud.net/…`.

**7.** В приложении: Настройки → «Общее состояние через облачную функцию» → вставить этот URL → «Сохранить». То же самое проделывает каждый участник — URL у всех один.

### Где менять схему, если бэкенд Herald Chat устроен иначе

Вся сетевая часть собрана в одной функции `api()` в `storage.js` — она просто шлёт `{action, ...params}` на `cfg.url`. Если у реального бэкенда Herald Chat другие имена действий или форма ответа — правится `Storage.pull()` / `Storage.push()` / `Storage.check()`, остальной код приложения (`app.js`) их не касается.

Разрешение конфликтов простое: побеждает состояние с более свежим `updatedAt`. Для четверых человек, которые отмечаются раз в день, этого достаточно; если начнутся гонки — придётся мержить по отдельным дням.

## Видео

Каждый может записать короткий ролик прямо в приложении (кнопка «＋» на вкладке «Сегодня» → блок «Видео дня») и посмотреть чужие видео за последние `VIDEO_RETENTION_DAYS` дней (по умолчанию 5). Работает только при включённой облачной синхронизации — без неё блок видео покажет подсказку и всё.

В модалке записи одна кнопка «● Запись», при нажатии становится «■ Стоп». Рядом «⟳ Камера» (переключить фронтальную/тыльную) и «🖼 Галерея» (взять готовое видео вместо записи с нуля). Лимит — 1 минута на ролик, видно прямо в интерфейсе жёлтой полосой.

**Почему запись, а не системная камера.** Видео с камеры iPhone «как есть» — это 4K/HDR и десятки–сотни мегабайт на минуту. Приложение вместо этого пишет через `MediaRecorder` с явно урезанным разрешением (~480×640) и битрейтом (~700 кбит/с) — получается заметно легче независимо от модели телефона, и заливается быстрее. Важный нюанс: если битрейт не задавать явно, Safari на iPhone по умолчанию пишет с 10 Мбит/с — выше, чем Chrome/Firefox (2.5 Мбит/с).

**Видео из галереи сжимается ради скорости, с защитой от повтора старого бага.** Раньше canvas + Web Audio для перекодирования готового видео один раз дали пустой (0 КБ) результат без единой ошибки на конкретном устройстве. `PCVideo.compressFile()` после сборки результата проверяет его размер против ожидаемого минимума для заявленной длительности — пустой или подозрительно маленький результат считается сбоем, а не успехом, и на любой сбой `app.js` просто отправляет исходный файл без изменений. Файлы младше 2.5 МБ сжатие не трогает вообще — уже маленькие. Это только про скорость загрузки на мобильной сети, не про надёжность проигрывания — та больше не зависит от размера файла (см. ниже).

### Хранилище видео — Yandex Object Storage, не Диск

Видео **физически хранится не на том же Диске**, что состояние и чат, а в отдельном бакете **Yandex Object Storage** (S3-совместимое хранилище). Причина — в истории версий ниже, если коротко: временные ссылки Яндекс.Диска (`/resources/download`) несколько раз подряд подводили именно на видео (не проигрывались, отдавали 403, требовали то `attachment`, то `inline`), а путь «прогнать байты через саму функцию» физически ограничен телом ответа Cloud Function (3.5 МБ) — минутный ролик в него никогда не влезет. Object Storage — то, для чего сделаны presigned-ссылки: полноценный `PUT`/`GET` с поддержкой Range для `<video>`, без самодельных обходов, без ограничения по размеру файла.

**Разовая настройка (один раз на весь чат):**

1. **Создать бакет.** Yandex Cloud Console → **Object Storage** → «Создать бакет», например `pc-sport-videos`. Доступ на чтение можно оставить приватным — все ссылки клиенту выдаются подписанными (presigned), публичный доступ не нужен.
2. **Создать статический ключ доступа.** IAM → выбрать (или создать) сервисный аккаунт с ролью `storage.editor` на этот бакет → «Создать статический ключ доступа». Получите `Access Key ID` и `Secret Access Key` — они не протухают сами по себе (в отличие от OAuth-токена Диска), поэтому Lockbox для них не нужен, обычных переменных окружения функции достаточно.
3. **Переменные окружения функции (новые, в дополнение к уже описанным для Диска):**
   - `S3_BUCKET` — имя бакета из шага 1;
   - `S3_ACCESS_KEY` — Access Key ID из шага 2;
   - `S3_SECRET_KEY` — Secret Access Key из шага 2.
4. **Деплой изменился.** Видео-код использует `boto3` — библиотеку нужно ставить через `pip`, а это работает только при деплое **ZIP-архивом**, не через вставку кода в веб-редактор. В архив (или в папку, если используете CLI/консоль с загрузкой директории) должны попасть **оба** файла из `backend/`: `index.py` и `requirements.txt` рядом, на одном уровне. Cloud Functions сам поставит зависимости при создании новой версии.

### Настройка Timer-триггера — авто­удаление старых видео

Без этого шага видео физически никогда не удалятся — очистка (`cleanup_old`) существует как действие функции, но сама по себе не запускается.

1. Yandex Cloud Console → **Cloud Functions** → открыть функцию → вкладка **Триггеры** → создать **Timer-триггер**.
2. Cron-выражение — раз в сутки ночью, например `0 3 * * ? *`.
3. Payload триггера (тело запроса, которое он пошлёт в функцию): `{"action":"cleanup_old"}`.
4. Сохранить. Дальше расписание работает само — руками ничего запускать не нужно.

**Переменная окружения (необязательная):**
- `VIDEO_RETENTION_DAYS` — сколько дней хранить видео, по умолчанию `5`.

### История версий — почему видео переехало на Object Storage

Если интересно, что именно перепробовано на самом Диске до переезда (и почему это не сработало) — коротко, по хронологии:

- **v6–v9.** Загрузка на Диск заработала сразу и стабильно. Воспроизведение — нет: Диск по умолчанию отдаёт ссылку с `disposition=attachment` («скачай файлом»), `<video>` с такой ссылкой не проигрывает.
- **v8.** Попытка подменить `disposition=attachment` на `inline` прямо в строке уже подписанного URL — предположение было, что подпись Диска не зависит от query-параметров. Предположение оказалось неверным: подмена ломала подпись целиком, отсюда `403` при любом обращении к ссылке начиная именно с этой версии — баг жил незамеченным несколько итераций.
- **v10–v13.** Добавлено действие `get_video_bytes`: для роликов до ~2 МБ функция сама скачивала файл и отдавала его байты в теле ответа (base64 → `blob:` на клиенте). Работало для маленьких файлов, но упиралось в лимит тела ответа Cloud Function (3.5 МБ) — принципиально не могло закрыть более длинные ролики.
- **v14.** Найдена и убрана подмена `disposition` из v8 — часть проблем ушла, но ограничение по размеру для `get_video_bytes` осталось.
- **v19.** Обнаружился разрыв между порогом «сжимать/не сжимать» на клиенте и порогом `get_video_bytes` на бэкенде — файлы, попадающие в этот разрыв, играли через капризную прямую ссылку и иногда не открывались (реальный кейс: код ошибки 4 в плеере, затем «Страница недоступна» на прямой ссылке).
- **v20.** По явному требованию — любой ролик до 1 минуты должен гарантированно открываться, без исключений по размеру. Латать дальше временные ссылки Диска смысла не было: видео переехало на Object Storage целиком, `get_video_bytes` и вся логика деления на «маленькие/большие» файлы удалены за ненадобностью — один путь работает для файла любого размера.
- **v22.** После переезда на S3 в общем индексе (`videos/index.json`) остались вперемешку старые записи с эры Диска (путь вида `app:/pc-sport/videos/...`) и новые с S3 (путь вида `videos/...`) — индекс общий, сам он не пересоздавался. Старые записи были видны в списке, но не открывались (путь не проходил проверку на S3-действиях). `_load_video_index()` теперь сам отбрасывает записи с недействительным путём при каждой загрузке и сразу сохраняет очищенную версию — самолечится при первом же открытии «Видео дня» после обновления, вручную ничего чистить не нужно.
- **v23.** Чат был виден одновременно на всех вкладках, не только на своей. Причина — не в логике переключения (`show()` в `app.js` всегда была верной), а в CSS: `#v-chat{display:flex;...}` задан селектором по id, а показ/скрытие вкладок работает через классы (`.view{display:none} .view.on{display:block}`) — id-селектор в CSS всегда весомее классового, поэтому это правило показывало чат постоянно, независимо от класса `on`. Переписано на `.view.on#v-chat{...}` (совпадает по специфичности логике остальных вкладок) плюс добавлен защитный барьер `.view:not(.on){display:none !important;}`, чтобы такой класс ошибок не повторялся, даже если где-то ещё случайно появится похожее правило по id.

## Уплотнение карточек на «Сегодня» (v28)

- Убрана подсказка «Отмечает только Х» под задизейбленными кнопками чужих участников — задизейбленные кнопки уже сами по себе понятны, отдельная строка текста только съедала место без новой информации.
- Карточка участника была в два ряда: имя+бейджи сверху, крупное число повторений (34px) с упражнением отдельной строкой снизу. Теперь один ряд: имя слева, число повторений (19px, помельче) и упражнение справа от него, бейджи (отработка/статус) — над числом, тоже справа. Экономит примерно треть высоты каждой карточки.

## Оформление чата — перенесено из Herald Chat (v39)

По прямому запросу — визуальный стиль сообщений один в один списан с реального Herald Chat (получил ZIP-архив свежей версии, разобрал `<style>` и разметку сообщения в JS). Перенесена именно **вёрстка и стили**, не сама логика приложения — своих каналов, инвайтов от админа и прочей архитектуры Herald тут по-прежнему нет, только визуальный язык:

- **Тёмная тема — только у вкладки чата**, не у всего приложения целиком. Тот же принцип, что и у тёмной модалки записи видео (`.rec-box`) — самостоятельный «режим» внутри в целом светлого приложения, а не глобальная смена темы.
- **Группировка подряд идущих сообщений одного автора** (окно 5 минут, как в Herald и в самом Telegram) — имя и аватар показываются только у первого/последнего сообщения «пачки», остальные идут вплотную, без повторения.
- **Аватар — кружок с инициалом**, показывается только у последнего сообщения группы (низ пачки, как в Telegram), у остальных — пустой спейсер той же ширины, чтобы пузыри не «съезжали» по горизонтали. Цвет — фиксированный на четырёх участников (`PARTICIPANT_COLOR` в `app.js`), не хэш по id, как в Herald (там участников произвольное число, тут — всегда четыре известных).
- **Время утоплено в правый нижний угол пузыря** — тот самый приём из Telegram: `float:right` внутри текста сообщения, текст обтекает время вместо того, чтобы выделять под него отдельную строку.
- **Реакции внахлёст снизу пузыря** — отрицательный `margin-top` заводит чипы реакций под сам пузырь, как в Telegram.
- **Ответы на сообщения** — цитата внутри пузыря над текстом (цветная полоса слева, имя автора, превью), клик по цитате плавно прокручивает к исходному сообщению с кратким подсвечиванием рамки.
- **Пузыри без хвостика**, полностью скруглённые (14px) — версия Herald тоже без классического «хвостика», это современный стиль (как Telegram на Android), не iOS-стиль с уголком.

**Что не переносил.** Галочки прочтения (одна/две серые/синие — статус доставки и прочтения) — в Herald это завязано на потоварный учёт версий прочтения по каждому участнику канала, у нас такого механизма пока нет и его создание — это уже не про оформление, а про новую функциональность. Закреплённые сообщения, автодополнение упоминаний (`@Имя`), контекстное меню по правому клику — тоже не переносил, не было в запросе и не требуется для четырёх участников с фиксированными именами.

## Настоящий push на iPhone, счётчик непрочитанных, ответы на сообщения (v38)

**Web Push — работает, даже когда приложение полностью закрыто.** Раньше «Включить уведомления» просто запрашивал разрешение браузера (`Notification.requestPermission()`) — этого хватало, только пока вкладка жива хотя бы в фоне. Теперь кнопка оформляет полноценную push-подписку: браузер регистрирует `PushSubscription` через `pushManager.subscribe()`, она уходит на бэкенд и привязывается к конкретному участнику. При каждом новом сообщении в чате функция сама рассылает push всем подписанным, кроме автора — это происходит на сервере, независимо от того, открыто ли у получателя приложение вообще.

**Критичное ограничение на iPhone.** Push доступен **только** для приложения, добавленного на «Экран Домой» (Safari → «Поделиться» → «На экран "Домой"») — из обычной вкладки Safari push не приходит никогда, это ограничение самого iOS 16.4+, а не наше. Если кто-то пользуется через обычную вкладку/закладку — кнопка включения либо не сработает, либо подписка оформится, но уведомления всё равно не придут. Проверить просто: приложение должно открываться без адресной строки Safari сверху, как отдельное окно.

**Разовая настройка (один раз на весь бэкенд):**

1. Ключи уже сгенерированы **в однострочном формате** — DER, закодированный в base64url, а не PEM с переносами строк (хотя `pywebpush` понимает и то, и другое, однострочный формат надёжнее вставлять в поле переменной окружения, где перенос строки может потеряться при копировании). Публичный уже встроен в `storage.js` (`Storage.push.VAPID_PUBLIC_KEY`) — трогать не нужно. Приватный **нигде в коде не хранится** (это было бы небезопасно) — он был показан один раз в переписке при генерации; если потерялся, проще сгенерировать новую пару заново и обновить публичный ключ в `storage.js` тоже (это одна пара, менять только приватный нельзя) — старые push-подписки при этом придётся оформить заново, но это не проблема, кнопка одна.
2. Переменные окружения функции — добавить к уже существующим:
   - `VAPID_PRIVATE_KEY` — приватный ключ (секрет, только сервер);
   - `VAPID_PUBLIC_KEY` — публичный ключ (не секрет, но пусть тоже будет для порядка);
   - `VAPID_SUBJECT` — контакт вида `mailto:твой-email@пример.ру`, формальное требование стандарта Web Push, на работу не влияет, любой рабочий адрес подойдёт.
3. `requirements.txt` пополнился `pywebpush` — деплой снова строго ZIP-архивом (уже был таким из-за `boto3`, ничего нового в способе деплоя).
4. Каждый участник — Настройки → «Включить уведомления» **после того**, как приложение добавлено на «Экран Домой» и открыто именно оттуда, а не из вкладки Safari.

**Счётчик непрочитанных — не просто точка, а число, и прямо в ленте.** При открытии вкладки «Чат» перед первым непрочитанным сообщением появляется красный делитель «▲ N новых» — видно ровно то место, докуда дочитал в прошлый раз. Технически это снимок (`unreadSnapshot`), посчитанный **до** того, как список помечается прочитанным — иначе делитель нечего было бы показывать, он бы стирался раньше, чем успевал отрисоваться.

**Бейдж на иконку приложения.** `navigator.setAppBadge()` — то самое красное число поверх иконки на «Экране Домой», как у обычных приложений. Обновляется синхронно со счётчиком на вкладке «Чат», сбрасывается при прочтении. Тоже требует установки через «Добавить на экран Домой» — для обычной вкладки Safari эта API недоступна.

**Ответы на сообщения.** Кнопка «↩» под любым сообщением — открывает панель с превью цитируемого сообщения над полем ввода, «✕» в этой панели отменяет. Отправленное сообщение показывает исходное над своим текстом (имя автора + до 80 символов превью). Если исходное сообщение к этому моменту выпало из локального кэша (например, очень старое) — просто «Ответ на сообщение» без содержимого, не ошибка.

## Реакции и видео прямо в ленте чата (v36)

Запрос был — перенести всю логику общения из Herald Chat. Полного переноса не делал: там своя система каналов, приглашения от админа, пагинация истории — для четырёх человек со статичной идентификацией это лишняя сложность, которая ничего не решает. Вместо этого — то, что реально просили: реакции и удобное обсуждение видео.

**Реакции.** Пять эмодзи (👍 ❤️ 😂 🔥 💪) под любым сообщением — и текстовым, и видео-карточкой. Тап по «😊+» открывает выбор, тап по уже стоящей реакции переключает на другую или снимает свою же повторным нажатием. Одна реакция на человека на сообщение — не как в Slack с несколькими сразу, попроще.

Технический нюанс: чат опрашивается «начиная с такого-то id», чтобы не перекачивать всю историю каждые 8 секунд — но это означает, что сервер никогда не пришлёт заново сообщение, которое клиент уже видел, даже если на нём поменялись реакции. Раз в 4 тика (~раз в 32 секунды) опрос идёт полностью, без `since` — специально, чтобы чужие реакции на старые сообщения долетали, а не оставались видны только тому, кто сам недавно листал историю.

**Видео как карточка в чате, не текстовое уведомление.** Раньше при загрузке видео в чат уходило «✅ Загрузил видео на Диск» — просто текст. Теперь загруженное видео становится настоящим сообщением: миниатюра, бейдж с количеством повторений, тап открывает плеер прямо из чата — и под этим сообщением можно реагировать и переписываться, как под любым другим. «Начал загрузку…» и сообщение об ошибке остались текстовыми — это переходные статусы, их не нужно обсуждать, только доложить.

## Зеркало на фронталке, кнопки синхронизации на «Сегодня» (v35)

**Зеркалирование фронтальной камеры.** Раньше запись с фронтальной камеры сохранялась ровно так, как её физически видит объектив — то есть поднятая правая рука на видео выглядела поднятой левой, текст на одежде читался задом наперёд. Это не баг был, а стандартное поведение камеры без обработки — но не то, что все привыкли видеть в зеркале и в других приложениях с фронталкой. Исправлено на двух уровнях:

- **Живой предпросмотр** (пока снимаешь, ещё не нажал «Запись») — зеркалится чисто на экране через CSS (`transform:scaleX(-1)`), сам поток с камеры не трогается.
- **Сама запись** — зеркалится по-настоящему, в пикселях: кадры с камеры перерисовываются на `canvas` зеркально (`ctx.scale(-1,1)`) и уже с этого canvas идут в `MediaRecorder`, а не напрямую с камеры. Это важно — если бы зеркалили только экран, файл, который потом смотрят другие, остался бы незеркальным, и то, что человек видел при съёмке, не совпадало бы с тем, что видят зрители.

Работает только для фронтальной камеры (`facing === 'user'`) — задняя камера идёт старым, более лёгким путём без лишней перерисовки на canvas, там зеркалить нечего.

Честная оговорка: постоянная перерисовка кадров на canvas в течение всей записи (до 60 секунд) — это дополнительная нагрузка на процессор и батарею по сравнению с прежним прямым потоком с камеры. На современных телефонах разницы заметно быть не должно, но на слабых/старых устройствах фронтальная запись теперь может ощутимо нагружать телефон сильнее, чем задняя. Не могу проверить это на реальном слабом устройстве — если кто-то заметит подтормаживание или нагрев именно на фронтальной записи, дай знать.

**Кнопки синхронизации переехали.** «Загрузить»/«Выгрузить» были в Настройках, отдельными кнопками. Теперь одна кнопка «↻ Обновить» на вкладке «Сегодня», сверху — делает оба действия разом (сначала выгружает то, что накопилось локально, потом подтягивает свежее с сервера и сливает). Обратная связь — через индикатор синхронизации в шапке (виден на любой вкладке), не только в Настройках.

## Критичный баг: чужие отметки стирались при синхронизации (v34)

**Что произошло.** Утром Антон, Артур и Коля отметили норму — всё синхронизировалось нормально. Позже Ваня открыл приложение и **сразу**, ещё до того как сам что-то нажал, увидел, что ни у кого нет отметок (хотя видео Коли были на месте). Он отметил свою норму и загрузил видео — после этого отметки Антона, Артура и Коли пропали у всех, не только у него.

**Причина.** `Storage.merge()` при каждом открытии приложения сравнивал два состояния — локальную копию на телефоне и то, что реально лежит в облаке — и брал **целиком** то, у которого поле `updatedAt` новее. Проблема в том, что `updatedAt` берётся из часов конкретного телефона (`new Date()` в браузере), а не с сервера. Если на телефоне Вани лежала старая локальная копия (например, приложение долго не открывали) или часы были попросту неточны — при слиянии эта устаревшая копия могла «победить» свежие данные с чужих телефонов **целиком, одним куском**. Отметки Антона/Артура/Коли пропали из вида уже на этом шаге, ещё до того как Ваня что-либо нажал — это ровно то, что он и описал. А когда он затем поставил свою галочку, локальный `commit()` проставил новый `updatedAt` (снова с его телефона) и отправил на сервер эту версию — без чужих отметок — навсегда затерев их в общем состоянии, не только у себя.

Видео эта история не задела, потому что видео живут в отдельном механизме — индекс самовосстанавливается сверкой с реальным содержимым S3-бакета (см. `_reconcile_index`), а не сравнением «чьё состояние новее целиком». Ровно поэтому видео Коли уцелели, а отметки — нет: у них были принципиально разные механизмы синхронизации.

**Исправление — слияние по отдельной записи, не по всему объекту.** `days` теперь сливаются день за днём, участник за участником: для каждой пары (дата, участник) записи с локального и с серверного телефона сравниваются между собой отдельно, и конфликт (случай, когда один и тот же человек в один день отмечен по-разному на двух телефонах — редкость) решается по времени **этой конкретной записи** (у неё уже есть собственное поле `at`), а не по времени всего объекта. Если один телефон вообще не трогал какую-то запись — она просто берётся с той стороны, где есть, без сравнения. Итог: даже если на одном телефоне часы совсем не те, он может задеть максимум те ячейки, которые сам редактировал — не всё состояние целиком.

Проверено на модели, повторяющей ровно сценарий Вани (пустая устаревшая локальная копия с часами, убежавшими на сутки вперёд, против свежего состояния с тремя отметками) — после слияния все три чужие отметки на месте, и после отправки Ваниной правки на сервере остаются все четыре, не одна.

**Вторая линия защиты — предупреждение о расхождении часов.** `ping` и `get_state` теперь возвращают серверное время; клиент сверяет его со своими часами при каждой синхронизации и, если расхождение больше 3 минут, пишет предупреждение в лог (Настройки → Логи) — не чаще раза в 10 минут, чтобы не спамить. Это не критично для защиты от бага (её теперь обеспечивает сама логика слияния), но полезно для диагностики — если на чьём-то телефоне реально сбиты часы, это будет видно сразу, а не только по последствиям.

**Что не тронуто.** Список участников и общие настройки (штраф, лимит альтернатив, дедлайн) по-прежнему сливаются по старой схеме — «версия с телефона, где `updatedAt` свежее» целиком. Это осознанный компромисс: эти поля редко меняются и почти никогда параллельно с разных телефонов (обычно правишь их ты один в Настройках), риск на порядок ниже, чем у `days`, где правки идут каждый день с четырёх телефонов одновременно.

## Три доработки по видео (v32)

**1. Видео из галереи весило по 70 МБ вместо ожидаемых 2–9 МБ.** Порог «файл уже маленький, сжимать не будем» тут ни при чём (2.5 МБ, 70 МБ явно выше — файл шёл через `compressFile()`). Вероятная причина глубже: гарантия «браузер уважает заданный `videoBitsPerSecond`» проверена и надёжно работает для потока **с камеры** (`startRecording`, живая запись) — но сжатие готового файла из галереи идёт через другой путь, `canvas.captureStream()` + Web Audio, а не поток с камеры. Судя по всему, на части устройств браузер не ограничивает битрейт так же строго для canvas-потока — сжатие технически «срабатывает» (не пустой файл, не ошибка), но по факту почти не уменьшает размер. Настоящей более надёжной замены этому конвейеру без тяжёлых зависимостей (вроде `ffmpeg.wasm`, ~25 МБ и заметная нагрузка на телефон) нет — вместо того чтобы делать вид, что сжатие сработало, теперь честно сравнивается результат: если файл после «сжатия» уменьшился меньше чем на 40% — в сообщении прямо написано «Сжатие почти не сработало на этом устройстве», а не тихая ложная уверенность.

**2. «Сохранить в галерею» теперь доступно сразу, не только после сбоя.** Раньше кнопка появлялась только в самом крайнем случае — когда все три попытки отправки провалились. Теперь есть кнопка «📥» прямо на экране предпросмотра, рядом с «Ещё раз»/«Отправить» — можно подстраховаться заранее, до того как вообще пытаться отправить.

**3. Контроль за реальным удалением старых видео.** Раньше приходилось просто верить, что Timer-триггер действительно чистит старое раз в сутки. Теперь:
- Настройки → «Почистить старые видео сейчас» — тот же `cleanup_old`, что и у триггера, только по нажатию, а не по расписанию. Показывает, сколько реально удалено (или «нечего удалять»).
- На миниатюре видео, до истечения срока хранения которого остался день или меньше, — маленькая красная плашка «сегодня»/«завтра».
- Число дней хранения в настройках теперь берётся из реального ответа сервера (`VIDEO_RETENTION_DAYS`), а не зашито в тексте — если поменяешь переменную окружения на бэкенде, интерфейс сам покажет актуальное число.

## Автозакрытие нормы по количеству повторений (v31)

Если при отправке видео указано число повторений и оно **достигает или превышает** текущую норму участника на эту дату — сразу вопрос: «Норма выполнена (X из Y) — закрыть день как «Норма»?». При «Да» день отмечается автоматически, без отдельного похода на вкладку «Сегодня» ставить галочку руками.

Норма берётся из той же функции `task()`, что считает число на карточке «Сегодня» — значит учитывает всё, что учитывает она: чередование упражнений у Коли/Вани (подтягивания/отжимания через день) и множитель отработки после признанного форс-мажора (×2/×3/×4). Если у Коли в этот день из-за отработки норма ×2 = 120 подтягиваний, а он ввёл 100 — вопрос не появится; введи он 120 и больше — появится.

Проверка пропускается, если день уже отмечен как «Норма» — не переспрашивает повторно.

## Скорость проигрывания, звук и качество записи (v30)

- **Скорость проигрывания** — четыре кнопки под видео в плеере: 0.5× / 1× / 1.5× / 2×. Просто `video.playbackRate`, ничего сложного. Сбрасывается на 1× при каждом новом открытии плеера.
- **Звук вкл/выкл при записи** — кнопка «🎤 Звук: вкл/выкл» в модалке записи. Технически — `stream.getAudioTracks().forEach(t => t.enabled = ...)`, без пересоздания камеры и без повторного запроса разрешений: `MediaRecorder` уважает `track.enabled` динамически, выключенная дорожка пишется тишиной, а не отсутствует вовсе. Можно переключать до записи и прямо во время неё.
- **Три уровня сжатия** — Сильное / Среднее / Слабое, кнопки рядом со звуком. Разное разрешение и битрейт: сильное — 360×480 при 350 кбит/с (минутный ролик ~2.5 МБ), среднее — 480×640 при 700 кбит/с (как было по умолчанию, ~5 МБ), слабое — 640×854 при 1300 кбит/с (~9.3 МБ, заметно четче). Выбор запоминается в `localStorage` между сессиями. Применяется одинаково и к живой записи, и к сжатию видео из галереи — один и тот же параметр в обоих местах `video.js`.
- **Крестик на удалении — снова крестик, не урна.** В прошлой версии сменил на 🗑, чтобы не путать с закрытием плеера — но закрытие плеера в том же обновлении и так стало текстовой кнопкой «← Закрыть», путать больше не с чем. Вернул ✕. Подтверждение перед удалением осталось прежним и обязательным — называет участника и дату видео, отменить нельзя без явного «ОК» в диалоге.

## Пять мелких багов с реальных тестов (v27)

**Уточнение к пункту 3 (см. ниже) — фикс из v27 не сработал, настоящая причина найдена только в v29.** `#chat-log` не имеет собственного `overflow` — как и везде в приложении, скроллится вся страница (`body`), а не отдельный `div`. Попытка в v27 прокрутить `log.scrollTop = log.scrollHeight` была no-op на нескроллящемся элементе — просто ничего не делала, отсюда чат по-прежнему открывался «где-то посередине». Переписано на `window.scrollTo(0, document.body.scrollHeight)` во всех трёх местах, где это было нужно: открытие вкладки, довисание новых сообщений при чтении внизу, и прокрутка после отправки своего сообщения.

**1. Отметка «Норма» не улетела в облако, пока не нажали «Выгрузить» вручную.** Автосохранение ждёт 900 мс после последнего изменения, прежде чем реально отправить на Диск (чтобы не долбить функцию на каждый чих). Если человек ставит галочку и в первую секунду сворачивает приложение или переключается на другое — таймер в фоне может не успеть сработать вовремя, и отметка остаётся только локальной. Исправлено: `flushOnHide()` — если страница уходит из вида (`visibilitychange` → `document.hidden`, и на всякий случай ещё `pagehide` как более надёжный сигнал при полном закрытии на части браузеров) и есть несохранённые изменения (индикатор синка жёлтый) — сохранение запускается немедленно, не дожидаясь истечения обычной задержки.

**2. Загрузка видео из галереи «долго грузилась».** Наш конвейер сжатия для галереи технически не может идти быстрее, чем длится сам ролик — он буквально проигрывает видео в реальном времени, пока захватывает кадры на canvas. 60-секундный ролик сжимается не меньше 60 секунд — это не баг, но раньше это никак не объяснялось в интерфейсе и легко читалось как зависание. Сообщение теперь прямо говорит: «займёт примерно столько же времени, сколько длится сам ролик, это не зависание». Если проблема воспроизведётся снова после этого уточнения — значит дело не в ожидании, а в чём-то другом, тогда нужны логи именно этого случая.

**3. Чат открывался не в самом низу, а где-то посередине.** `renderChat()` полагался на эвристику «прокрутка уже была внизу» при каждой перерисовке — при первом открытии вкладки после переключения контейнер только что стал видимым, и его `scrollHeight`/`scrollTop` в этот момент ещё не отражают реальную раскладку, эвристика могла ошибочно решить, что прокручивать не нужно. Добавлена отдельная `scrollChatToBottom()`, которая вызывается явно при каждом открытии вкладки «Чат» (через двойной `requestAnimationFrame`, чтобы раскладка успела посчитаться) — независимо от эвристики.

**4. Нижняя панель вкладок иногда «отклеивалась» и скроллилась вместе со страницей.** Классический баг iOS Safari: если у `<input>` шрифт меньше 16px, при фокусе на нём телефон автоматически зумит страницу — и после такого зума `position: fixed` может перестать вести себя как фиксированный элемент, пока не поймать момент возврата масштаба. У нас было сразу три таких поля: `.panel input` (13px — все поля в настройках), `.rec-reps-row input` (15px — повторения при отправке видео) и `.chat-input input` (15px — сообщение в чате). Все подняты до 16px — порог, ниже которого iOS начинает зумить.

**5. Разработчики боялись смотреть видео из-за крестика — думали, что удалит.** Дело было не в самой кнопке удаления (на миниатюре, с подтверждением) — она и так требует подтверждения. Дело в том, что крестик **закрытия плеера** (когда уже смотришь видео) выглядел один в один как крестик удаления, и это порождало страх «а вдруг это она». Разделено визуально: закрытие плеера (и заодно закрытие модалки записи, для единообразия) теперь текстовая кнопка «← Закрыть», не крестик. Кнопка удаления на миниатюре осталась крестиком, но сменила иконку на 🗑, чтобы визуально не путаться ни с чем «просто закрывающим», и подтверждение стало конкретнее — называет участника и дату видео, а не общую фразу.

## Надёжность видео и дополнительные возможности (v26)

По итогам реальных тестов (человек потерял подход из-за бага и вынужден был переснимать) — несколько важных исправлений и новых возможностей.

**Критичный баг — картинка «замирала», звук продолжался.** Причина: `MediaRecorder.start()` без аргумента копит все данные видео внутри буфера и сбрасывает их одним куском только в конце записи. На роликах длиннее ~20 секунд это на части устройств (подтверждено на iPhone) провоцирует известный баг реализации `MediaRecorder`: видеодорожка начинает терять кадры под давлением на внутренний буфер, аудио продолжает писаться нормально — отсюда именно такая картина (видео стоит, звук идёт). Исправлено: `rec.start(1000)` — данные сбрасываются каждую секунду вместо накопления до конца. Поправлено в обоих местах, где идёт запись через `MediaRecorder` — живая съёмка и сжатие видео из галереи (`video.js`).

**Надёжная догрузка — по аналогии с Telegram/WhatsApp.** Раньше при сбое сети запись видео просто предлагалось отправить ещё раз вручную. Теперь:
- Сам `PUT`-запрос заливки повторяется автоматически до 3 раз с паузой при сетевом сбое — «сеть прервалась» на мобильной сети чаще означает «попробуй ещё раз», а не «файл потерян».
- Blob кладётся в **IndexedDB** ещё ДО первой попытки отправки и удаляется оттуда только после подтверждённого успеха — значит переживает даже полное закрытие приложения посреди обрыва связи. При следующем запуске (и при возврате в приложение из фона) `resumePendingVideos()` сам, без участия человека, пытается дозалить всё, что осталось в очереди.
- Если и это не помогло — ролик не потерян: кнопка **«📥 Сохранить в галерею»** (через `navigator.share` с файлом, на iOS/Android обычно предлагает «Сохранить в Фото»; если `share` недоступен — обычная ссылка на скачивание) плюс кнопка **«↻ Повторить отправку»**.

**Новые возможности:**
- Поле **«Повторений»** (необязательное) в модалке записи — число прикрепляется к видео и видно рядом с миниатюрой в списке и в самом плеере.
- **Миниатюра** — кадр из ролика, автоматически захватывается через canvas сразу после готовности предпросмотра, хранится прямо в записи индекса как небольшая JPEG-картинка (десятки КБ, отдельная загрузка в S3 не нужна). Если по какой-то причине не собралась — остаётся значок «▶», как раньше.
- **Удаление видео** — кнопка «✕» на миниатюре, видна только на своих видео (та же идентичность, что и везде в приложении), с подтверждением. Новое действие бэкенда `delete_video` убирает файл из бакета и из индекса.

**Известное ограничение.** Миниатюры хранятся прямо в `videos/index.json`, который целиком возвращается клиенту при каждом открытии «Видео дня». Для масштаба этого приложения (4 человека, окно хранения 5 дней) это некритично — даже несколько десятков видео с миниатюрами укладываются в десятки–сотни КБ, далеко от лимита ответа функции (3.5 МБ). Если когда-нибудь дневник разрастётся сильно больше — это то место, на которое стоит посмотреть первым.

## Кто я — обязательный вход, закреплено, сброс объявляется в чат (v24–v25)

Выбор «кто я» раньше влиял только на чат — отметки дня и загрузка видео были никак не защищены, любой мог отметить чужой день или записать видео за другого участника (v24). По дальнейшему запросу пошли дальше — идентичность теперь закреплена, а не просто выбрана (v25):

- **Вход обязательный.** Пока идентичность не выбрана, поверх всего приложения висит модалка «Кто я в приложении?» без кнопки закрытия — ничего не работает, пока не выбрал. Открывается сама при каждом запуске, если идентичность не установлена.
- **Обычным способом её не поменять.** Кнопка «Кто я?» в шапке, если идентичность уже закреплена, ничего не открывает — только подсказывает, что менять нужно через Настройки. В Настройках вместо всегда открытой сетки выбора — имя текстом и кнопка «Сбросить идентичность» с подтверждением.
- **Каждая установка объявляется в общий чат.** Самый первый выбор на устройстве — спокойным сообщением («🔒 Артур закрепил(а) за собой это устройство»). Любой следующий выбор (то есть после явного сброса через настройки) — тревожным («⚠️ На этом телефоне идентичность сбрасывали и выбрали заново: …, если это не ты — напиши в чат»). Разница между «первый раз» и «уже было» — отдельный флаг `identityEverSet` в `localStorage`, который **не** очищается при сбросе самой идентичности (`Storage.identity.reset()` трогает только текущее значение, не флаг) — это и даёт возможность отличить один случай от другого.
- **Отметки дня** (вкладки «Сегодня» и «Журнал»): кнопки статуса для чужих участников — задизейблены визуально и заблокированы в обработчике клика (двойная защита, на случай если кто-то снимет `disabled` через инструменты разработчика).
- **Запись видео**: кнопка «＋» на чужой карточке в «Видео дня» не показывается вообще; `openRecorder()` дополнительно проверяет совпадение участника с идентичностью на входе.

**Честная оговорка про уровень защиты.** Это по-прежнему ограничение на уровне интерфейса, не крипто-авторизация — своего логина в приложении нет (см. архитектуру с самого начала), и бэкенд не проверяет, кто на самом деле вызвал `send_message`/`get_upload_url` с каким `participantId`. `localStorage` можно очистить в настройках браузера в обход кнопки «Сбросить» — тогда флаг `identityEverSet` тоже исчезнет, и следующий выбор снова пройдёт как «первый», без тревожного сообщения. Это подделываемо технически подкованным человеком, как и любая чисто клиентская защита без сервера — задача не в неприступности, а в том, чтобы случайный/спонтанный обман был виден всем в чате, а не остался незамеченным.

## Чат (v16)

Отдельная вкладка «Чат» — тот же принцип, что и у видео: общий файл на Диске (`chat.json`), два действия бэкенда:

- `send_message({participantId, text})` → `{ok: true, message}`
- `get_messages({since?})` → `{items: [...]}` — без `since` отдаёт всё, с `since` (id последнего уже известного сообщения) — только новые

Обрезка старше 500 сообщений (`CHAT_MAX_MESSAGES`), лимит длины одного сообщения — 2000 символов.

**«Кто я».** Своего логина в приложении нет и не появилось — как и у отметок дня и у видео, это просто локальный выбор участника на телефоне (Настройки → «Я в чате», или сразу при первом открытии вкладки «Чат»). Ничего не синхронизируется, у каждого свой выбор на своём устройстве.

**Опрос, а не push.** Cloud Functions — это запрос-ответ, без постоянного соединения. Пока открыта вкладка «Чат», приложение опрашивает `get_messages` раз в 8 секунд (`since` = id последнего известного сообщения — не перекачивает всю историю на каждый тик). При переключении на другую вкладку опрос останавливается — незачем дёргать функцию впустую.

**Автосообщения о видео.** При старте и завершении загрузки в чат от лица того, кто грузит, летит «🎥 Начал загрузку видео на Диск…» / «✅ Загрузил видео на Диск» (или «⚠️ Не получилось загрузить видео: …» при сбое). Отправка этих сообщений не блокирует и не может сорвать саму загрузку видео — если чат недоступен, в лог просто попадёт предупреждение, загрузка видео на это никак не влияет.

**Уведомления — с оговоркой.** Кнопка «Включить уведомления» в Настройках запрашивает разрешение через `Notification API`. Когда приложение свёрнуто (фоновая вкладка, но браузер работает) и приходят новые сообщения — показывается системное уведомление и бейдж на вкладке «Чат». Важное ограничение: это работает, только пока браузер/PWA физически открыты хотя бы в фоне. Уведомления при полностью закрытом приложении и заблокированном телефоне — это отдельная задача (Web Push API + VAPID-ключи + хранение push-подписок + отправка push из самой функции), заметно более тяжёлая по объёму работы, здесь её нет.

## Логи (v16)

`log.js` — журнал событий, копится в `localStorage` на телефоне, до 400 последних записей. `PCLog.info/warn/error(текст)` — так помечаются события из остального кода.

**Логируется автоматически, без ручной расстановки по каждому месту:** любой неудачный вызов облачной функции — прямо внутри общей `api()` в `storage.js`. Отдельно добавлено: каждое автосохранение состояния (старт/успех/ошибка), каждая попытка загрузки видео (старт/успех/сбой, с указанием участника и размера), сбои чата.

**Настройки → «Логи»** — моноширинная панель с последними записями (ошибки красным, предупреждения жёлтым), кнопки «Скопировать» (в буфер обмена, с запасным вариантом через `textarea` + `execCommand` для браузеров без `navigator.clipboard`) и «Очистить». Если что-то не работает — самый быстрый способ разобраться дальше: скопировать отсюда и прислать текстом, а не описывать словами или скриншотом одной строки ошибки.

**Индикатор синхронизации** — маленькая точка в шапке рядом с часами, видна на всех вкладках: серая (только локально) → жёлтая пульсирующая (сохраняю) → зелёная (сохранено на Диске) → красная (ошибка сохранения).

## Кэш и обновления (важно)

Service worker раньше отдавал файлы приложения «сначала из кэша», и после каждого обновления на GitHub люди по факту продолжали видеть старую версию, пока вручную не чистили данные сайта в Safari. Начиная с `pcsport-v5` стратегия обратная — «сначала сеть»: пока телефон в сети, всегда подгружается свежий код с GitHub Pages, а кэш используется только как запасной вариант, если сети совсем нет. После деплоя новой версии обновление должно долетать без ручной чистки кэша — но первый раз после этого изменения саму чистку один раз всё равно стоит сделать (Настройки → Safari → Дополнения → Данные сайтов → удалить для `nikitsmm.github.io`), чтобы слезть со старого service worker'а, который ещё помнит прежнюю схему.

### Номер версии на экране

В шапке приложения (видна на всех вкладках, серым мелким текстом рядом с названием) — номер версии и дата, например `v6 · 17.08.2026`. Это статичный текст прямо в `index.html`, не через JS — значит его видно и глазами на телефоне, и по одному только просмотру исходного HTML, без выполнения скриптов.

**Правило на будущее:** при каждой правке, которая уходит в файлы `pc-sport-pwa`, версия в шапке (`index.html`, `id="appVersion"`) и версия кэша (`sw.js`, `var CACHE = 'pcsport-vN'`) бампаются на одно и то же число синхронно. После деплоя достаточно взглянуть на номер в шапке (или попросить прислать его текстом/скриншотом) — если он совпадает с тем, что было в последнем ответе, значит файлы на GitHub обновились; если старый — деплой не долетел или закэширован.

## Известные ограничения

- Пока URL функции не задан, приложение работает в локальном режиме: данные живут на устройстве, перенос между устройствами — через «Выгрузить JSON» / «Загрузить JSON» в настройках. Видео в локальном режиме недоступны в принципе.
- Функция должна быть с публичным вызовом (без IAM), иначе фронтенд не сможет её дёрнуть напрямую — тот же принцип, что и у `BACKEND_URL` в Herald Chat.
- Если `refresh_token` в Lockbox станет недействителен (например, доступ приложению отозвали в аккаунте Яндекса), функция вернёт `server_misconfigured` — тогда бутстрап из шага 4 нужно повторить.
- Запись видео требует разрешения на камеру/микрофон и `MediaRecorder` — не работает в старых браузерах и не работает через `file://` (нужен HTTPS, GitHub Pages подходит).
- Голосование по форс-мажору происходит в чате, приложение только фиксирует результат.
