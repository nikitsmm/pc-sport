# ПЦ Спорт — PWA

Одностраничное приложение для челленджа: нормы на день, отработка после форс-мажора, журнал и счёт по штрафам. Без сборки — статика, любой хостинг.

## Навигация (v18)

Внизу — четыре вкладки: Сегодня, Журнал, Чат, Настройки. Счёт и Правила — компактные кнопки сверху на «Сегодня»; на кнопке «Счёт» сразу видна общая сумма долгов, не нужно заходить внутрь. Чат живёт только внизу, в одном месте — не дублируется больше нигде (было по ошибке сразу в двух местах с одинаковым `id="chat-dot"` — HTML такого не допускает, это баг предыдущей версии).

## Что считает само

- **Чередование.** У Коли и Вани подтягивания и отжимания идут через день от опорной даты (настройки → «Отсчёт чередования»). По умолчанию 17.08.2026 — день подтягиваний.
- **Отработка.** Каждый подряд идущий день со статусом «Форс» повышает множитель следующего дня: ×2 → ×3 → ×4, дальше не растёт. На карточке видно и итог, и разбор (`60 × 3`).
- **Штрафы.** Пропуск и добровольный выход дают 5000 ₽, которые делятся поровну между теми, кто участвует в челлендже **на дату штрафа**. Выбывшие в делёж не попадают. Вкладка «Счёт» показывает баланс каждого: сколько заплатил, сколько получил, сколько в итоге.
- **Альтернативы.** Считает израсходованные за неделю (пн–вс) и подсвечивает превышение лимита в 2 раза.

Статус дня ставится на вкладке «Сегодня» или тапом по клетке в журнале (перебор по кругу).

## Развёртывание на GitHub Pages

1. Залить содержимое папки в репозиторий, например `nikitsmm/pc-sport`.
2. Settings → Pages → Source: `main`, папка `/root`.
3. Открыть `https://nikitsmm.github.io/pc-sport/` на телефоне → «Поделиться» → «На экран "Домой"».

HTTPS обязателен: без него не заработают ни service worker, ни установка на домашний экран.

## Синхронизация — по схеме Herald Chat

Токенов в приложении нет вообще. Клиент знает только URL одной облачной функции и делает один вид запроса:

```
POST <URL функции>
{ "action": "get_state" | "save_state" | "ping", ...params }
```

Сама функция (папка `backend/`) сама лезет в Яндекс.Диск и в Lockbox за токеном — токен не хранится статичной строкой нигде, включая переменные окружения: там лежит только `refresh_token`, а рабочий `access_token` функция обновляет сама и складывает обратно в Lockbox. В браузер не попадает ничего.

### Разовая настройка бэкенда (один раз на весь чат)

Архитектура — точная копия Herald Chat: OAuth-токен Яндекс.Диска не лежит статичной строкой в переменной окружения (он всё равно протухает раз в год), а хранится в **Yandex Lockbox** вместе с `refresh_token` и сам обновляется функцией по мере истечения. Функция читает Lockbox через IAM-токен своего сервисного аккаунта — человек в эту цепочку не входит вообще.

**1. OAuth-приложение Яндекса.**
На https://oauth.yandex.ru/ → «Создать приложение» → веб-сервис, права `cloud_api:disk.read` + `cloud_api:disk.write`, Callback URL можно `https://oauth.yandex.ru/verification_code`. Получить `Client ID` и `Client Secret`.

**2. Секрет в Yandex Lockbox.**
В консоли облака создать секрет с одним ключом `state` (тип «текст»), значение пока любое — перезапишется на шаге 4. Запомнить `LOCKBOX_SECRET_ID`.

**3. Сервисный аккаунт.**
Создать сервисный аккаунт с ролями `lockbox.payloadViewer` и `lockbox.editor`. Привязать его к будущей Cloud Function (на шаге 5).

**4. Бутстрап — получить первый refresh_token.**
Разово, вручную, с компьютера:
```
# открыть в браузере и авторизоваться под тем аккаунтом Яндекса,
# на чьём Диске будет жить состояние челленджа:
https://oauth.yandex.ru/authorize?response_type=code&client_id=<CLIENT_ID>

# Яндекс покажет код подтверждения — обменять его на токены:
curl -X POST https://oauth.yandex.ru/token \
  -d grant_type=authorization_code \
  -d code=<КОД_ИЗ_БРАУЗЕРА> \
  -d client_id=<CLIENT_ID> \
  -d client_secret=<CLIENT_SECRET>
```
Ответ (`access_token`, `refresh_token`, `expires_in`) собрать в JSON вида
`{"access_token":"…","refresh_token":"…","expires_at":<unix-время истечения>}`
и записать этой строкой в ключ `state` секрета Lockbox (шаг 2). Дальше функция обновляет его сама — вручную это нужно сделать один раз.

**5. Yandex Cloud Function.**
Среда `python3.12`, обработчик `index.handler`, привязать сервисный аккаунт из шага 3. **Деплой строго ZIP-архивом** — из-за `boto3` (нужен для видео, см. «Хранилище видео» ниже) через веб-редактор код не задеплоить, pip install оттуда не запускается. В архив (или в загружаемую директорию) кладутся `backend/index.py` и `backend/requirements.txt` рядом, на одном уровне.

**Переменные окружения функции:**
- `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` — из шага 1;
- `LOCKBOX_SECRET_ID` — из шага 2;
- `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` — для видео, см. раздел «Хранилище видео» ниже (можно добавить позже, если сначала хочется поднять только состояние/чат).

**6. Публичный доступ** — включить вызов без IAM-токена (публичная функция), скопировать URL вида `https://functions.yandexcloud.net/…`.

**7.** В приложении: Настройки → «Общее состояние через облачную функцию» → вставить этот URL → «Сохранить». То же самое проделывает каждый участник — URL у всех один.

### Где менять схему, если бэкенд Herald Chat устроен иначе

Вся сетевая часть собрана в одной функции `api()` в `storage.js` — она просто шлёт `{action, ...params}` на `cfg.url`. Если у реального бэкенда Herald Chat другие имена действий или форма ответа — правится `Storage.pull()` / `Storage.push()` / `Storage.check()`, остальной код приложения (`app.js`) их не касается.

Разрешение конфликтов простое: побеждает состояние с более свежим `updatedAt`. Для четверых человек, которые отмечаются раз в день, этого достаточно; если начнутся гонки — придётся мержить по отдельным дням.

## Видео

Каждый может записать короткий ролик прямо в приложении (кнопка «＋» на вкладке «Сегодня» → блок «Видео дня») и посмотреть чужие видео за последние `VIDEO_RETENTION_DAYS` дней (по умолчанию 5). Работает только при включённой облачной синхронизации — без неё блок видео покажет подсказку и всё.

В модалке записи одна кнопка «● Запись», при нажатии становится «■ Стоп». Рядом «⟳ Камера» (переключить фронтальную/тыльную) и «🖼 Галерея» (взять готовое видео вместо записи с нуля). Лимит — 1 минута на ролик, видно прямо в интерфейсе жёлтой полосой.

**Почему запись, а не системная камера.** Видео с камеры iPhone «как есть» — это 4K/HDR и десятки–сотни мегабайт на минуту. Приложение вместо этого пишет через `MediaRecorder` с явно урезанным разрешением (~480×640) и битрейтом (~700 кбит/с) — получается заметно легче независимо от модели телефона, и заливается быстрее. Важный нюанс: если битрейт не задавать явно, Safari на iPhone по умолчанию пишет с 10 Мбит/с — выше, чем Chrome/Firefox (2.5 Мбит/с).

**Видео из галереи сжимается ради скорости, с защитой от повтора старого бага.** Раньше canvas + Web Audio для перекодирования готового видео один раз дали пустой (0 КБ) результат без единой ошибки на конкретном устройстве. `PCVideo.compressFile()` после сборки результата проверяет его размер против ожидаемого минимума для заявленной длительности — пустой или подозрительно маленький результат считается сбоем, а не успехом, и на любой сбой `app.js` просто отправляет исходный файл без изменений. Файлы младше 2.5 МБ сжатие не трогает вообще — уже маленькие. Это только про скорость загрузки на мобильной сети, не про надёжность проигрывания — та больше не зависит от размера файла (см. ниже).

### Хранилище видео — Yandex Object Storage, не Диск

Видео **физически хранится не на том же Диске**, что состояние и чат, а в отдельном бакете **Yandex Object Storage** (S3-совместимое хранилище). Причина — в истории версий ниже, если коротко: временные ссылки Яндекс.Диска (`/resources/download`) несколько раз подряд подводили именно на видео (не проигрывались, отдавали 403, требовали то `attachment`, то `inline`), а путь «прогнать байты через саму функцию» физически ограничен телом ответа Cloud Function (3.5 МБ) — минутный ролик в него никогда не влезет. Object Storage — то, для чего сделаны presigned-ссылки: полноценный `PUT`/`GET` с поддержкой Range для `<video>`, без самодельных обходов, без ограничения по размеру файла.

**Разовая настройка (один раз на весь чат):**

1. **Создать бакет.** Yandex Cloud Console → **Object Storage** → «Создать бакет», например `pc-sport-videos`. Доступ на чтение можно оставить приватным — все ссылки клиенту выдаются подписанными (presigned), публичный доступ не нужен.
2. **Создать статический ключ доступа.** IAM → выбрать (или создать) сервисный аккаунт с ролью `storage.editor` на этот бакет → «Создать статический ключ доступа». Получите `Access Key ID` и `Secret Access Key` — они не протухают сами по себе (в отличие от OAuth-токена Диска), поэтому Lockbox для них не нужен, обычных переменных окружения функции достаточно.
3. **Переменные окружения функции (новые, в дополнение к уже описанным для Диска):**
   - `S3_BUCKET` — имя бакета из шага 1;
   - `S3_ACCESS_KEY` — Access Key ID из шага 2;
   - `S3_SECRET_KEY` — Secret Access Key из шага 2.
4. **Деплой изменился.** Видео-код использует `boto3` — библиотеку нужно ставить через `pip`, а это работает только при деплое **ZIP-архивом**, не через вставку кода в веб-редактор. В архив (или в папку, если используете CLI/консоль с загрузкой директории) должны попасть **оба** файла из `backend/`: `index.py` и `requirements.txt` рядом, на одном уровне. Cloud Functions сам поставит зависимости при создании новой версии.

### Настройка Timer-триггера — авто­удаление старых видео

Без этого шага видео физически никогда не удалятся — очистка (`cleanup_old`) существует как действие функции, но сама по себе не запускается.

1. Yandex Cloud Console → **Cloud Functions** → открыть функцию → вкладка **Триггеры** → создать **Timer-триггер**.
2. Cron-выражение — раз в сутки ночью, например `0 3 * * ? *`.
3. Payload триггера (тело запроса, которое он пошлёт в функцию): `{"action":"cleanup_old"}`.
4. Сохранить. Дальше расписание работает само — руками ничего запускать не нужно.

**Переменная окружения (необязательная):**
- `VIDEO_RETENTION_DAYS` — сколько дней хранить видео, по умолчанию `5`.

### История версий — почему видео переехало на Object Storage

Если интересно, что именно перепробовано на самом Диске до переезда (и почему это не сработало) — коротко, по хронологии:

- **v6–v9.** Загрузка на Диск заработала сразу и стабильно. Воспроизведение — нет: Диск по умолчанию отдаёт ссылку с `disposition=attachment` («скачай файлом»), `<video>` с такой ссылкой не проигрывает.
- **v8.** Попытка подменить `disposition=attachment` на `inline` прямо в строке уже подписанного URL — предположение было, что подпись Диска не зависит от query-параметров. Предположение оказалось неверным: подмена ломала подпись целиком, отсюда `403` при любом обращении к ссылке начиная именно с этой версии — баг жил незамеченным несколько итераций.
- **v10–v13.** Добавлено действие `get_video_bytes`: для роликов до ~2 МБ функция сама скачивала файл и отдавала его байты в теле ответа (base64 → `blob:` на клиенте). Работало для маленьких файлов, но упиралось в лимит тела ответа Cloud Function (3.5 МБ) — принципиально не могло закрыть более длинные ролики.
- **v14.** Найдена и убрана подмена `disposition` из v8 — часть проблем ушла, но ограничение по размеру для `get_video_bytes` осталось.
- **v19.** Обнаружился разрыв между порогом «сжимать/не сжимать» на клиенте и порогом `get_video_bytes` на бэкенде — файлы, попадающие в этот разрыв, играли через капризную прямую ссылку и иногда не открывались (реальный кейс: код ошибки 4 в плеере, затем «Страница недоступна» на прямой ссылке).
- **v20.** По явному требованию — любой ролик до 1 минуты должен гарантированно открываться, без исключений по размеру. Латать дальше временные ссылки Диска смысла не было: видео переехало на Object Storage целиком, `get_video_bytes` и вся логика деления на «маленькие/большие» файлы удалены за ненадобностью — один путь работает для файла любого размера.

## Чат (v16)

Отдельная вкладка «Чат» — тот же принцип, что и у видео: общий файл на Диске (`chat.json`), два действия бэкенда:

- `send_message({participantId, text})` → `{ok: true, message}`
- `get_messages({since?})` → `{items: [...]}` — без `since` отдаёт всё, с `since` (id последнего уже известного сообщения) — только новые

Обрезка старше 500 сообщений (`CHAT_MAX_MESSAGES`), лимит длины одного сообщения — 2000 символов.

**«Кто я».** Своего логина в приложении нет и не появилось — как и у отметок дня и у видео, это просто локальный выбор участника на телефоне (Настройки → «Я в чате», или сразу при первом открытии вкладки «Чат»). Ничего не синхронизируется, у каждого свой выбор на своём устройстве.

**Опрос, а не push.** Cloud Functions — это запрос-ответ, без постоянного соединения. Пока открыта вкладка «Чат», приложение опрашивает `get_messages` раз в 8 секунд (`since` = id последнего известного сообщения — не перекачивает всю историю на каждый тик). При переключении на другую вкладку опрос останавливается — незачем дёргать функцию впустую.

**Автосообщения о видео.** При старте и завершении загрузки в чат от лица того, кто грузит, летит «🎥 Начал загрузку видео на Диск…» / «✅ Загрузил видео на Диск» (или «⚠️ Не получилось загрузить видео: …» при сбое). Отправка этих сообщений не блокирует и не может сорвать саму загрузку видео — если чат недоступен, в лог просто попадёт предупреждение, загрузка видео на это никак не влияет.

**Уведомления — с оговоркой.** Кнопка «Включить уведомления» в Настройках запрашивает разрешение через `Notification API`. Когда приложение свёрнуто (фоновая вкладка, но браузер работает) и приходят новые сообщения — показывается системное уведомление и бейдж на вкладке «Чат». Важное ограничение: это работает, только пока браузер/PWA физически открыты хотя бы в фоне. Уведомления при полностью закрытом приложении и заблокированном телефоне — это отдельная задача (Web Push API + VAPID-ключи + хранение push-подписок + отправка push из самой функции), заметно более тяжёлая по объёму работы, здесь её нет.

## Логи (v16)

`log.js` — журнал событий, копится в `localStorage` на телефоне, до 400 последних записей. `PCLog.info/warn/error(текст)` — так помечаются события из остального кода.

**Логируется автоматически, без ручной расстановки по каждому месту:** любой неудачный вызов облачной функции — прямо внутри общей `api()` в `storage.js`. Отдельно добавлено: каждое автосохранение состояния (старт/успех/ошибка), каждая попытка загрузки видео (старт/успех/сбой, с указанием участника и размера), сбои чата.

**Настройки → «Логи»** — моноширинная панель с последними записями (ошибки красным, предупреждения жёлтым), кнопки «Скопировать» (в буфер обмена, с запасным вариантом через `textarea` + `execCommand` для браузеров без `navigator.clipboard`) и «Очистить». Если что-то не работает — самый быстрый способ разобраться дальше: скопировать отсюда и прислать текстом, а не описывать словами или скриншотом одной строки ошибки.

**Индикатор синхронизации** — маленькая точка в шапке рядом с часами, видна на всех вкладках: серая (только локально) → жёлтая пульсирующая (сохраняю) → зелёная (сохранено на Диске) → красная (ошибка сохранения).

## Кэш и обновления (важно)

Service worker раньше отдавал файлы приложения «сначала из кэша», и после каждого обновления на GitHub люди по факту продолжали видеть старую версию, пока вручную не чистили данные сайта в Safari. Начиная с `pcsport-v5` стратегия обратная — «сначала сеть»: пока телефон в сети, всегда подгружается свежий код с GitHub Pages, а кэш используется только как запасной вариант, если сети совсем нет. После деплоя новой версии обновление должно долетать без ручной чистки кэша — но первый раз после этого изменения саму чистку один раз всё равно стоит сделать (Настройки → Safari → Дополнения → Данные сайтов → удалить для `nikitsmm.github.io`), чтобы слезть со старого service worker'а, который ещё помнит прежнюю схему.

### Номер версии на экране

В шапке приложения (видна на всех вкладках, серым мелким текстом рядом с названием) — номер версии и дата, например `v6 · 17.08.2026`. Это статичный текст прямо в `index.html`, не через JS — значит его видно и глазами на телефоне, и по одному только просмотру исходного HTML, без выполнения скриптов.

**Правило на будущее:** при каждой правке, которая уходит в файлы `pc-sport-pwa`, версия в шапке (`index.html`, `id="appVersion"`) и версия кэша (`sw.js`, `var CACHE = 'pcsport-vN'`) бампаются на одно и то же число синхронно. ## Известные ограничения

- Пока URL функции не задан, приложение работает в локальном режиме: данные живут на устройстве, перенос между устройствами — через «Выгрузить JSON» / «Загрузить JSON» в настройках. Видео в локальном режиме недоступны в принципе.
- Функция должна быть с публичным вызовом (без IAM), иначе фронтенд не сможет её дёрнуть напрямую — тот же принцип, что и у `BACKEND_URL` в Herald Chat.
- Если `refresh_token` в Lockbox станет недействителен (например, доступ приложению отозвали в аккаунте Яндекса), функция вернёт `server_misconfigured` — тогда бутстрап из шага 4 нужно повторить.
- Запись видео требует разрешения на камеру/микрофон и `MediaRecorder` — не работает в старых браузерах и не работает через `file://` (нужен HTTPS, GitHub Pages подходит).
- Голосование по форс-мажору происходит в чате, приложение только фиксирует результат.
